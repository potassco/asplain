Contrastive Explanation Generation Task
You will be given a contrastive explanation graph that represents the differences between two models: the real model (what actually happened) and the hypothetical model (what would have happened if the user's query were true). Your goal is to generate a short and intuitive natural language explanation that clearly communicates why the queried fact is or isn't part of the model.

System Overview
Input:

A logic program that solves a problem.
A stable model, which is a set of true atoms.
A user query, stating what they expected to be true or false.
An explanation preference, which determines what can be modified to make the query hold.
A contrastive explanation graph, which shows the differences between the real and hypothetical models.

The contrastive explanation graph consists of:

node(A), representing atoms (facts).
edge(N, N', ID), representing relationships between facts.
attr(T, N, A, V), providing additional attributes,
    where T is either node or edge, N is the identifier of the node or edge, A is the attribute name and V the value

Graph Semantics & Attributes

The contrastive explanation graph compares two models:

The real model, which represents what actually happened.
The hypothetical model, which represents what would have happened if the query were satisfied.
Each node and edge has attributes:

For Nodes (attr(node, N, A, V)):

origin=[real, hypothetical]: Indicates whether the fact is present in the real model, hypothetical model, or both.
abduced=[add, rm]:
    If abduced=add, this fact had to be assumed true for the query to be satisfied.
    If abduced=rm, this fact had to be removed to satisfy the query.
query=[include, exclude]:
    include: The user wanted this fact to be true.
    exclude: The user wanted this fact to be false.

For Edges (attr(edge, N, A, V)):

type=[cause, inhibitor, reciprocal_inhibitor]:
    cause: The first fact supports the second.
    inhibitor: The first fact prevents the second.
    reciprocal_inhibitor: The two facts mutually prevent each other.
rule_id=numeric identifier for the rule
rule_vars=values that should substitute variables in rule_str
rule_str=string representation of the original rule in ASP using clingos syntax


Explanation Generation Rules
Your explanation should be a short and intuitive natural language summary of why the query is true or false, following these rules:

* Use Simple, Succinct Language

    The explanation should be one or two sentences.
    Use plain, natural language that anyone can understand.
    Example:
    Incorrect: "The real model contains X, but the hypothetical model required Y to be abduced for the query to hold."
    Correct: "For X to happen, we have to assume Y was true."

* Treat Abduced Facts as Necessary Assumptions

    All abduced facts must be referenced in the explanation since they are necessary for the query to hold.
    If a fact has abduced=add, the explanation must treat it as something that was not originally true but had to be assumed in the hypothetical scenario for the query to be satisfied.
    The explanation should make this clear by using phrasing like "would have led to" or "would have caused" instead of directly stating that the fact happened.
    Example:
    Incorrect: "For Clare to be sentenced to prison, she must have resisted the authority, which led to her punishment."
    Correct: "For Clare to be sentenced to prison, she must have resisted the authority, which would have led to her punishment."

    If a fact had abduced=add, it did not actually happen in the real world but had to be introduced in the hypothetical world. This must be reflected in the wording:

    Use "would have led to" instead of "led to."
    Use "would have been necessary" instead of "was necessary."

    Similarly, if a fact had abduced=remove, it means it would have to be removed for the hypothetical world to happen.
    Example:
    Correct: "For Clare to be innocent, she should not have drunk alcohol."

* Mention query in text

    Is important to mention the query in the text to let the user know what they asked.
    Example for query included:
    Incorrect: "James should have been poisoned"
    Correct: "For James to die, he should have been poisoned"

    Example for query excluded:
    Incorrect: "James should have been on holidays"
    Correct: "For James to not die, he should have been on holidays"

* Integrity constraints rules

    If an edge has type=reciprocal_inhibitor, check whether attribute: rule_str of the edge that joins the two nodes contains a meaningful reason for the constraint.
    If so, include that reason in the explanation instead of just stating that a fact was removed.
    For details about the values of variables P1, P2 and E1, one can check the attribute rule_vars

    Example:
    For a rule like #false :- friend(P1,P2), age(P1,E1), age(P2,E2), E1-E2>10.
    the explanation should capture the general conflict that P1 and P2 can't be friend since P1 is at least 10 years older than P2.
    Example:
    For a rule like #false :- friend(P1,P2), friend(P1,E1), enemy(P2,E1).
    the explanation should capture the general conflict that P1 and P2 can't be friend since P1 is a friend of E1 who is an enemy of P2.
    If rule_vars is (anna,mario,fernando) then the explanation would be:
    Anna and Mario can't be friend because anna is a friend of fernando and mario and fernando are enemies.

    Notice how the rule makes sure E1 is the same value in both friend(P1,E1) and enemy(P2,E1) on the constraint.

    The explanation for the constraint should never default to a generic meaning, but always look for a more specific reason exists rule_str and rule_vars.



* Ignore Unrelated Nodes

    Only explain facts that are connected to the query.
    Do not include isolated or irrelevant facts.

* Avoid Any Mention of Graph Structure or Formal Concepts

    Do NOT mention:
    Abduction, inhibitors, causal links
    Graph structure (nodes, edges)
    Rules, rule numbers, predicates with parentheses
    DO use clear, natural language explanations.


Examples:

Example 1: Removing a Cause
Input Graph:
    node(d).
    node(h).
    node(p).
    attr(edge,0,rule_vars,()).
    attr(edge,0,rule_str,"p :- d; not a.").
    attr(edge,0,rule_id,1).
    attr(edge,0,type,cause).
    attr(edge,0,origin,real).
    attr(node,p,query,exclude).
    attr(node,d,abduced,rm).
    attr(node,h,origin,hypothetical).
    attr(node,d,origin,real).
    attr(node,h,origin,real).
    attr(node,p,origin,real).
    edge(d,p,0).
Predicates:
    p: James was poisoned
    d: James drank the drinks
    h: James was on holiday
    a: James was administered the antidote

Explanation:
    "If James hadn't drunk his drink, he would not have been poisoned."

Explanation:
    "If James had been on holiday he wouldn't had gotten the antidote. So if he had drank then drink while on holiday, then we would have been punished."

Example 3: Prevented via constraint
Input Graph:
    node(sit(anna)).
    node(stand(anna)).
    node(person(anna)).
    node(age(anna,50)).
    attr(edge,0,rule_vars,(anna,)).
    attr(edge,1,rule_vars,(anna,anna)).
    attr(edge,0,rule_str,"{ sit(P); stand(P) } :- person(P).").
    attr(edge,1,rule_str,"#false :- sit(P); stand(P'); P = P'.").
    attr(edge,0,rule_id,1).
    attr(edge,1,rule_id,2).
    attr(edge,1,type,reciprocal_inhibitor).
    attr(edge,0,type,cause).
    attr(edge,0,origin,hypothetical).
    attr(node,stand(anna),query,include).
    attr(node,sit(anna),abduced,rm).
    attr(node,stand(anna),origin,hypothetical).
    attr(node,sit(anna),origin,real).
    attr(node,person(anna),origin,real).
    attr(node,person(anna),origin,hypothetical).
    attr(node,age(anna,50),origin,real).
    attr(node,age(anna,50),origin,hypothetical).
    edge(person(anna),stand(anna),0).
    edge(sit(anna),stand(anna),1).
Explanation:
    "For Anna to stand, she would need to stop sitting, since the same person cannot do both at the same time."

    "For Anna to stand, she would need to be younger than 90, as someone over that age cannot stand."
